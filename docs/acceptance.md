# Acceptance and evidence

**25 November 2026.** The equipment record covers a Raspberry Pi 5, Raspberry Pi OS 64-bit with a graphical desktop, a Windows 11 laptop and an iPhone connected to the Pi’s USB host. Windows USB SSH and a Windows-to-Pi application-socket echo were verified. Linux and usbmuxd identified one USB iPhone after releasing the Pi desktop’s camera mount. Apple host validation succeeded on product type `iPhone18,2` running iOS 27.2.1. The relay, iproxy and capture broker were running. The Pi display advertises 720×1280 at 60 Hz, and the trusted desktop capture launcher is installed.

The final deployment path is Windows endpoint → USB Ethernet → physical Pi relay → USB-only iproxy/usbmuxd → signed foreground iPhone endpoint. `PASS` records a successful execution in the stated scope. `FAIL` records a completed check with a negative outcome. `BLOCKED` identifies a specific unmet prerequisite. `NOT TESTED` means an execution or artifact has yet to be recorded.

## Complete the physical record

Use one traceable experiment ID for each mode × content type × direction. Record source commit and endpoint builds, measured route and capture interface, link type, UTC window, source size, captured size, delivery/ACK state, sender-to-final-ACK monotonic time, source and receiver hashes, marker visibility, authentication outcome, capture drops and limitations. Keep the artifact hash with the endpoint and relay logs. A complete 24-case functional matrix runs four modes, three payload types and two directions. Keep reconnect, power, concurrent transfers and controlled faults as separate cases.

The Linux loopback experiment starts isolated Python endpoints, forwards real TCP through the relay core and captures the two TCP legs. Its report and PCAPNGs can validate the instrumentation on the host that executed it. Report that host and transport; the end-to-end hardware gate requires the signed iPhone.
